# Подключить n8n

Сначала установите Stolas Core. Если настроена команда в PATH, запустите из любого каталога:

```sh
stolas integrate n8n
```

Без команды в PATH используйте `./stolas integrate n8n` из каталога установки.

## Ручной импорт

Выберите «Подготовить файл для импорта». Ключ n8n не требуется.
Мастер предлагает три размещения: Docker на хосте Stolas, приложение без Docker
на том же хосте и n8n на другом хосте. Для Docker используются обнаруженные
контейнер и локальный адрес связи; для приложения на том же хосте — по умолчанию
`127.0.0.1:8080`. Для другого хоста выберите локальный IPv4:порт Stolas из списка
или введите вручную. LAN и overlay-интерфейсы равноправны; Docker bridge отмечен
и находится в конце списка. Адрес проверяется реальной локальной привязкой,
занятый порт не меняется скрытно.

Listener (`STOLAS_LISTEN`, `STOLAS_PORT`) и endpoint для n8n задаются отдельно.
Обычно endpoint совпадает с listener; для настроенного вами reverse proxy можно
оставить listener `127.0.0.1:8080`, указав endpoint `https://stolas.example.test`.
HTTP через доверенную сеть разрешён после подтверждения: заголовок Authorization
передаётся без TLS. Для недоверенного транзита используйте HTTPS. `0.0.0.0`
не предлагается автоматически; ручной выбор требует отдельного подтверждения
и конкретного endpoint для клиента. Подтверждение сохраняется в `.env` как
`STOLAS_BIND_CONFIRMED=1`, чтобы штатное обновление сохранило выбранный listener.

Старые значения `lan`, `vpn`, `proxy` переводятся в размещение «другой хост»
с явным выбором сохранения текущего listener или его изменения. Endpoint
показывается повторно; широкая привязка не включается автоматически.
Смена адреса API показывается до подтверждения. Мастер не настраивает маршруты,
VPN, firewall, Docker-сети и reverse proxy.

Импортируйте `.stolas/integrations/n8n/local.json` в n8n. В HTTP Request узлах выберите Header Auth
credential с `Authorization: Bearer <токен Stolas из .env>`.
В Telegram-узле выберите существующий Telegram credential.
Выполните Manual test и затем включите расписание. Workflow по умолчанию неактивен.

## Подключение через API

Создайте API key в настройках n8n и введите его в отдельном мастере.
Ввод ключа виден в терминале для вставки; не показывайте эту сессию посторонним.
Ключ используется только в памяти во время подключения и не сохраняется в файлах/логах. Telegram Bot Token мастер
не спрашивает, не генерирует, не читает и не сохраняет.

Мастер читает страницы `GET /api/v1/credentials`, выбирает метаданные подходящих
Telegram/Header Auth credentials. Сначала выбирается проект, затем показываются только credentials с подтверждённой принадлежностью этому проекту. Единственный Telegram credential в выбранном проекте выбирается
автоматически. Неизвестный Header Auth всегда требует явного выбора из списка
с именами и ID, даже если он один. Только Header Auth, ранее созданный Stolas
и записанный по ID, переиспользуется автоматически. Секреты credentials не читаются. Проверка и POST выполняются
с правами вашего API key; `workflow:create` и `credential:list` должны быть разрешены.
Для явного создания собственного Header Auth дополнительно требуется `credential:create`.
Telegram credential никогда не создаётся.

Если credentials нет, создайте его в интерфейсе n8n и повторите команду.
Если версия n8n/права не позволяют прочитать список или проверить общий проект,
мастер оставляет файл для ручного импорта. Credentials из разных проектов
автоматически не связываются. Workflow создаётся неактивным; успешный POST
не заменяет Manual test и проверку отправки Telegram.

Список API credentials доступен не во всех версиях/ролях; поддержка проверена
с n8n 2.42.6. [Контракт API n8n](https://docs.n8n.io/api/api-reference/).

## Ошибки и повторный запуск

Ошибка интеграции не откатывает установку Core. При неудачной смене адреса API
мастер возвращает прежний `.env` и перезапускает только Stolas.
`.stolas/integrations/n8n/install-state.json` хранит ID созданных ресурсов. Известный workflow не
создаётся повторно. Если ответ POST потерян, запись `pending` останавливает
повтор: проверьте ресурсы в n8n и используйте ручной импорт.

Локальная Docker-связь проверяется аутентифицированным запросом из самого
контейнера n8n. Для удалённого n8n и task runners доступ подтверждает Manual test.
Сначала проверяется локальный listener: ошибка привязки/локальной авторизации
отличается от недоступного endpoint. Проверка URL с хоста Stolas не подтверждает
доступность с другого хоста; завершите Manual test в n8n.
Значения и политика сообщений хранятся в `.stolas/integrations/n8n/settings.json` без секретов.

Политики workflow: только проблемы, каждый замер, ежедневная сводка.
Интервал и час сводки настраиваются в отдельном мастере. Часовой пояс определяется автоматически из ОС хоста Stolas; мастер показывает IANA-имя и источник, не задаёт повторный вопрос и не изменяет ОС. TZ контейнера n8n и переменная TZ процесса мастера не переопределяют пояс хоста.
Telegram и расписание принадлежат n8n; Core отправкой сообщений не занимается.

## Суточный отчёт в Telegram

При выборе режима «ежедневная сводка» мастер создаёт workflow с русскоязычным
отчётом: узел, период в часовом поясе ОС хоста Stolas (IANA), средняя скорость загрузки
и отдачи в Мбит/с, число проверок и распределение результатов по понятным категориям.
Отдельно отмечаются подтверждённое снижение, снижение без подтверждения,
расхождение серверов, блокировка проверкой маршрута и недоступность измерения.
При отсутствии измерений или неполной статистике отчёт **не объявляет канал
исправным**. Статус «в пределах нормы» относится только к проведённым замерам.
Сводка берётся из `GET /v1/summary/daily` и не запускает дополнительный тест.

Форматирование выполняет узел `Format summary` встроенного шаблона
`n8n/stolas.json`. Для новых подключений мастер автоматически добавляет
часовой пояс ОС в настройки workflow и форматтеры уведомлений. **Ранее созданные workflow n8n
автоматически не обновляются**: существующий workflow нужно менять отдельно;
повторный запуск подключения не заменяет уже зарегистрированный workflow.

### Права n8n и изменение пояса ОС

Фильтрация списка credentials по выбранному проекту уменьшает раскрытие названий
посторонних credentials в мастере. Это только представление: API key должен иметь
минимально необходимые права, а разграничение проектов и RBAC обеспечивает n8n.
Если API не сообщает принадлежность credential проекту, автоматическая привязка
не выполняется; используйте ручной импорт. Секретные данные credentials не выводятся
и не сохраняются.

После изменения системного пояса выполните `stolas diagnose`, затем
`stolas integrate n8n`. CLI всегда перечитывает пояс ОС. Настройки расписания n8n
сохраняются внутри workflow и сами вслед за ОС не меняются. Мастер подготовит
`local.json` с новым поясом; существующий workflow не перезаписывается автоматически,
поскольку он мог быть изменён пользователем. В API-режиме выводится ссылка на уже
созданный workflow, дубликат не создаётся; код 2 означает необходимость ручного обновления.
Сохраните резервную копию workflow, перенесите настройки из файла в существующий
workflow, проверьте Header Auth/Telegram credentials, timezone и расписание,
выполните Manual test и опубликуйте изменения в n8n. Диагностика напоминает проверить
публикацию, если записанный при создании пояс workflow отличается от ОС; ручную
публикацию она не может подтвердить. API key повторно нужен только для работы с API,
он не хранится. В режиме export ключ не нужен.

При ручном импорте исходного `n8n/stolas.json` замените `REPLACE_WITH_OS_IANA_TIMEZONE`
в обоих Settings Code nodes и timezone в настройках workflow на IANA-пояс хоста.
Предпочтителен файл, созданный мастером: в нём все три значения согласованы.
