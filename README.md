# Stolas

Переносимый монитор скорости IPv4 TCP на iperf3. Linux + Docker, CLI с JSON и HTTP API для локального или удалённого n8n. Лицензия MIT. Никакой зависимости от конкретного маршрутизатора, провайдера или n8n в процессе агента.

## Интерактивная установка на Linux

Для установки **без Git** выполните в терминале целевого Linux-хоста:

```sh
curl -fsSL https://raw.githubusercontent.com/Lfyz-git/Stolas/v0.2.0/bootstrap.sh | sh
```

Рекомендуется закреплённый релиз **v0.2.0**: загрузчик и исходники одной версии. Загрузчик спросит каталог установки (по умолчанию `$HOME/stolas`), скачает архив релиза с GitHub, проверит SHA-256 из `SHA256SUMS` и запустит мастер. Нужны `curl` или GNU `wget`, `tar`, `sha256sum` и интерактивный терминал. Ошибка загрузки/контрольной суммы не запускает мастер. Тело загрузчика выполняется только после чтения завершающей строки функции; обрыв внутри неё не запускает частичный скрипт.

Если curl отсутствует, можно использовать wget:

```sh
wget -qO- https://raw.githubusercontent.com/Lfyz-git/Stolas/v0.2.0/bootstrap.sh | sh
```

Каталог можно передать сразу, вместе с режимом подготовки настроек:

```sh
curl -fsSL https://raw.githubusercontent.com/Lfyz-git/Stolas/v0.2.0/bootstrap.sh | sh -s -- --dir /opt/stolas
```

`/opt/stolas` может уже существовать: если он пуст и принадлежит вам, установка продолжится. Если каталога ещё нет, нужно право создать его в родительском каталоге. Например, администратор заранее выполняет `sudo install -d -o "$USER" -g "$(id -gn)" /opt/stolas`. Запускайте мастер обычным пользователем; sudo нужен только для системных пакетов/Docker. Пути с пробелами поддерживаются. По SSH используйте терминальную сессию (`ssh -t` для удалённой команды).

По умолчанию bootstrap загружает v0.2.0. Другой опубликованный релиз можно выбрать через `--ref vX.Y.Z`. Полный commit SHA или `--ref main` загружаются через codeload; для них передайте заранее проверенный SHA-256 архива через `--sha256 HASH`. `main` меняется и подходит для разработки; одинаковый релиз устанавливает одни исходники на разных хостах. Контрольная сумма по HTTPS обнаруживает повреждение архива, но не является отдельной криптографической подписью издателя. Можно скачать bootstrap в файл, изучить и затем выполнить `sh bootstrap.sh`.

При повторном запуске загрузчик предложит `reconfigure`, `update`, `rollback` или `cancel`. Каталог с посторонними файлами, symlink или опасный путь отклоняется без перезаписи. Два установщика не могут одновременно работать с одним каталогом. Повторная настройка из установленного проекта:

```sh
cd "$HOME/stolas"
sh install.sh --action reconfigure
```

Установку из Git checkout или предварительно распакованного архива также можно запустить напрямую:

```sh
sh install.sh
```

Мастер опросит пользователя о всех параметрах измерений из `config/example.json`: имени узла, длительности и потоках, таймаутах, повторах, проверке резервов, истории, локальном IPv4, проверках WAN. Для каждой группы — основной, дополнительной и аварийной — отдельно задаются способ выбора (`sequential`/`random`), количество серверов без верхнего ограничения, адреса, порты и пороги DL/UL. Затем запросит адрес и порт HTTP API, токен (Enter генерирует случайный либо сохраняет существующий) и вариант настройки n8n. Enter оставляет предложенное значение; `-` очищает необязательные bind/interface/gateway. Числа и адреса проверяются при вводе; вся конфигурация проверяется перед сохранением.

Мастер создаёт `.env` и `config/local.json`, устанавливает недостающий Docker Engine с Compose на **Ubuntu/Debian** через [официальный apt-репозиторий Docker](https://docs.docker.com/engine/install/ubuntu/#install-using-the-apt-repository), собирает образ, проверяет конфигурацию, запускает API и ждёт его готовности. На остальных Linux требуется заранее установленный локальный Docker Engine и Compose v2 с поддержкой `up --wait`. Поддерживаются amd64/arm64; удалённый Docker Engine не подходит. Для мастера нужен Python 3.10+; если Python отсутствует, оболочка предлагает установить его через apt. Для часовых поясов нужен системный пакет `tzdata`. Runtime Python и iperf3 устанавливаются внутри контейнера. Установка системных пакетов требует root/sudo; существующий Docker не заменяется и конфликтующие пакеты автоматически не удаляются.

В конце выполняется **один CLI-цикл скорости** через работающий контейнер, с теми же настройками и хранилищем, что у API. JSON результата и краткие DL/UL выводятся в терминал. Низкая скорость является результатом измерения, а `route_blocked`/`unavailable` дают предупреждение и exit 2. Ошибка установки или невозможность запуска CLI (например cooldown при повторном запуске мастера) дают exit 1. Автоматическое расписание в Stolas не включается.

Варианты настройки n8n:

- **`later` (по умолчанию)** — отложить. n8n не нужен для установки; мастер завершается после единичного CLI-теста. API остаётся запущенным. Позже можно импортировать исходный workflow по инструкции ниже либо повторить мастер.
- **`export`** — запросить URL Stolas, Telegram chat id, интервал 1–23 часа и IANA timezone, затем создать `n8n/local.json` для ручного импорта. В n8n нужно выбрать Header Auth и Telegram credentials.
- **`api`** — дополнительно запросить URL **уже существующего n8n**, его API key и токен Telegram-бота. Через [публичный API n8n](https://docs.n8n.io/api/) создаются два credentials и неактивный workflow. Ключу нужны права создания credentials и workflows. Ключ n8n и bot token вводятся скрыто и не сохраняются локально; API-токен Stolas остаётся в `.env` и credential store n8n. Мастер не устанавливает отдельный n8n и TLS reverse proxy.

В `export`/`api` мастер предложит схему подключения n8n, режим Telegram и час сводки. URL Stolas должен быть доступен **из n8n**. Для указанного локального Docker-контейнера проверяется `/healthz` из его network namespace; токен передаётся через stdin, не аргументы процесса. Для удалённого n8n проверка с установочного хоста не подтверждает доступ из n8n: завершите проверку через **Manual test**. Создание workflow не проверяет доставку Telegram. При `route.mode: "off"` WAN-alert отключён.

При повторной настройке старые файлы сохраняются рядом как `.bak-*` с правами 0600. `.env` также имеет 0600; конфигурация измерений читается контейнером uid 10001 и имеет 0644. Локальные workflow, состояние импорта и резервные копии исключены из Git и Docker context. `n8n/install-state.json` содержит ID созданных ресурсов без секретов: после частичного сбоя проверьте их в n8n. Повторное автоматическое создание при существующем state-файле блокируется, чтобы не плодить дубликаты. Если намеренно меняете API-токен после интеграции, обновите Header Auth credential в n8n.

Для подготовки настроек без установки, сети и теста скорости:

```sh
sh install.sh --configure-only
```

## Обновление и откат

Для обновления установленного каталога до закреплённого релиза:

```sh
curl -fsSL https://raw.githubusercontent.com/Lfyz-git/Stolas/v0.2.0/bootstrap.sh | sh -s -- --dir /opt/stolas --ref v0.2.0 --action update
```

При появлении следующего релиза замените обе версии в команде. Обновление заменяет исходники с резервной копией, сохраняет `.env`, `config/local.json`, настройки n8n, Compose project name и volume истории, пересобирает только Stolas и проверяет готовность API. Дополнительного теста скорости нет. Не используйте `update` для изменения параметров — выберите `reconfigure`; Enter сохраняет текущие значения. Обновление из checkout: получите нужные исходники в отдельный каталог и выполните там `sh install.sh --target /opt/stolas --action update`.

Откат последнего обновления исходников:

```sh
cd /opt/stolas
sh install.sh --action rollback
```

Откат восстанавливает исходники из `.stolas-backups`, пересобирает агент с текущими настройками и тем же volume. Поддерживаются обновления формата v0.2.0 и новее; резервные копии до изменения формата конфигурации проверяйте отдельно. Ошибка обновления возвращает старые исходники и пытается восстановить сервис; результат восстановления указан в `.stolas-install-status.json`. Не удаляйте `.stolas-backups` до проверки новой версии. Снятые upstream файлы автоматически не удаляются. При оборванной транзакции следующий запуск сначала восстанавливает исходники и просит повторить команду.

Чужие Compose проекты и volumes не меняются; имя проекта создаётся отдельно для каталога установки и сохраняется в `.env`. Для старой установки подхватывается её существующий проект. Обнаружение того же имени проекта у другого каталога останавливает установку. Не выполняйте `docker compose down -v`: это удалит историю Stolas.

## Подключение n8n

| Выбор мастера | Что указать | Где слушает Stolas |
| --- | --- | --- |
| `native` — n8n в ОС того же хоста | `http://127.0.0.1:8080` | localhost |
| `docker` — n8n в отдельном контейнере того же хоста | имя контейнера и IPv4 gateway его bridge-сети, например `172.20.0.1` | только указанный IPv4 |
| `lan` — n8n на другой машине | уже настроенный HTTPS endpoint | localhost за TLS proxy |
| `vpn` — доверенный туннель | IPv4 Stolas на VPN, например `10.8.0.1`, endpoint `http://10.8.0.1:8080` | только VPN IPv4 |
| `proxy` — HTTPS reverse proxy | HTTPS имя Stolas | localhost за TLS proxy |

Для Docker найдите сеть, не меняя её: `docker inspect --format '{{json .NetworkSettings.Networks}}' ИМЯ_N8N`. Поле `Gateway` bridge-сети обычно является адресом Linux-хоста. Этот адрес должен уже существовать на хосте; `localhost` контейнера не подходит. Разрешите в firewall доступ к выбранному порту только от n8n. Если контейнер использует host/macvlan/нестандартную сеть, используйте соответствующий адрес хоста или HTTPS proxy. Мастер не подключает Stolas к чужому Compose и не добавляет порт n8n.

Для LAN/HTTPS нужны DNS-имя, сертификат и TLS proxy на хосте Stolas (пример Caddy ниже). Для VPN сначала создайте доверенный туннель между хостами и проверьте маршрутизацию. Мастер не устанавливает proxy/VPN и не меняет Traefik. Он не выбирает `0.0.0.0` автоматически. Bearer-токен обязателен во всех схемах. У n8n с внешним task runner сетевое окружение Code-ноды может отличаться; HTTP Request-ноды должны достигать указанного endpoint из n8n.

Совместимость workflow проверяется импортом в **n8n 2.42.6**, закреплённый image digest хранится в CI. Используются штатные `httpHeaderAuth` (`name`, `value`) и `telegramApi` (`accessToken`). В режиме `api` мастер сверяет их схемы через публичный API n8n до создания ресурсов; при несовместимости выбирайте `export`. Для создания нужны права `credential:create`, `credential:read` (schema) и `workflow:create`, либо API key с соответствующими правами вашей редакции n8n. Автоматическая активация не выполняется.

## Ручной быстрый старт на Linux

```sh
cp .env.example .env
cp config/example.json config/local.json
python3 -c 'import secrets; print(secrets.token_urlsafe(32))'
```

Запишите сгенерированный токен в `.env` как `STOLAS_API_TOKEN`. В `config/local.json` задайте `node`, пороги скорости и `route.expected_public_cidrs`: разрешённый внешний IPv4 основного WAN в формате `/32` либо доверенный диапазон провайдера. При возможности задайте ожидаемые `route.interface` и `route.gateway`. Не копируйте реальные адреса и секреты в example-файлы.

```sh
docker compose build
docker compose up -d
docker compose logs --tail 30
```

Пример конфигурации намеренно не допускает тест до настройки WAN (`route_unconfigured`). Для лаборатории можно явно поставить `route.mode: "off"`; такие циклы никогда не дают `wan_alert: true`. Контейнер слушает только `127.0.0.1:8080`. Compose использует host networking **на Linux**, запускает uid 10001 без capabilities, с read-only rootfs. Не задавайте публичный адрес прослушивания без TLS, firewall и ограничений reverse proxy.

Для API нужен TLS reverse proxy на хосте либо доверенный VPN/SSH-туннель. Пример Caddy с собственным DNS-именем:

```caddyfile
stolas.example.invalid {
    reverse_proxy 127.0.0.1:8080 {
        transport http {
            response_header_timeout 610s
        }
    }
}
```

Замените имя на своё. Ограничьте доступ адресами n8n или доверенной сетью, лимитируйте запросы/соединения на proxy. Токен обязателен и при TLS. Если n8n тоже в Docker, его localhost не является localhost хоста: используйте доступное ему TLS-имя/туннель. Не подключайте Stolas к чужим Compose-проектам и не меняйте существующие сервисы.

## API

Все маршруты требуют `Authorization: Bearer <token>`. GET `/healthz` проверяет работоспособность HTTP-сервиса, **не** доступность WAN/iperf. GET `/v1/results/latest` возвращает последний цикл, GET `/v1/results` — последние 100 циклов. GET `/v1/summary/daily` читает предыдущие 24 часа сохранённой истории, не запускает измерение. POST `/v1/tests` запускает синхронный цикл, **без тела и параметров**. Адреса серверов нельзя передать через API. Timeout клиента должен быть больше `cycle_timeout` + 10 секунд.

```sh
curl --fail-with-body -X POST --max-time 250 \
  -H "Authorization: Bearer $STOLAS_API_TOKEN" \
  https://stolas.example.invalid/v1/tests
```

В этой команде переменная должна быть уже задана в shell; файл `.env` читается Compose, а не curl. Ответы: 401 — неверный токен, 409 — уже идёт тест, 429 — cooldown, 400 — непустое тело, 500 — внутренняя ошибка. Успешно завершённый цикл возвращает HTTP 200 даже при недоступности измерений: проверяйте `status`. Не повторяйте POST автоматически после timeout: цикл мог продолжиться; сначала прочтите latest. Одна файловая блокировка на общий каталог данных защищает от наложения CLI/API/планировщика. Не запускайте несколько независимых каталогов данных для одного канала.

## CLI и расписание

Python 3.12+, iperf3 и iproute2; Python-зависимостей из PyPI нет.

```sh
python3 -m agent validate --config config/local.json
python3 -m agent run --config config/local.json --data data
python3 -m agent history --data data
python3 -m agent schedule --config config/local.json --data data
```

`run`: exit 0 — ok, 2 — цикл сохранён с иным статусом, 1 — ошибка конфигурации/хранилища, busy или cooldown. stdout — JSON, диагностическая ошибка — JSON stderr. `schedule` запускает цикл сразу и через три часа после завершения предыдущего. Для фиксированных часов используйте n8n (каждые 3 часа) или cron. Выберите **один** планировщик; API сам по себе тесты не запускает.

Разовый запуск через работающий контейнер:

```sh
docker compose exec stolas python3 -m agent run
docker compose exec stolas python3 -m agent history
```

## Что и как измеряется

1. Серверы разделены на `server_groups.primary` (основные), `additional` (дополнительные) и `emergency` (аварийные). Обычный цикл выбирает основной сервер. Если сервер недоступен, перебираются остальные в его группе; после исчерпания основных — дополнительные, затем аварийные. После первого полного DL/UL без просадки обычный цикл заканчивается. В примере HOSTKEY — основной, МТС — дополнительный, RUWEB — аварийный. HOSTKEY использует 5201–5209; МТС 3333; RUWEB 5201. `attempts_per_server: 2` ограничивает обычные ошибки измерения; отдельный `busy_attempts_per_server: 9` разрешает при занятости перейти к следующим разрешённым портам. Оба бюджета настраиваются от 1 до 9; их сумма и `cycle_timeout` ограничивают смешанные ошибки. При первом успешном полном DL/UL оставшиеся порты не проверяются.
2. Каждый заход: download (`-R`), затем upload, IPv4 TCP, 4 потока по 10 секунд. Результат пары привязан к одному разрешённому IPv4 и порту. Пары с разных серверов не объединяются; частичные/невалидные измерения сохраняются.
3. `server_busy` исключает занятый порт из оставшихся попыток текущего сервера; после исчерпания портов/бюджета выбирается следующий сервер. Сервер с одним занятым портом повторно не опрашивается в этом цикле. Timeout и прочие ошибки расходуют отдельный небольшой бюджет. В `attempts` сохраняются порт, ошибка и `switch_reason`: `next_port_busy`, `busy_ports_exhausted`, `retry_measurement`, `measurement_attempts_exhausted`. Недоступность всех серверов означает `unavailable`, а не диагноз WAN.
4. Скорость ниже порога основного замера проверяется независимым сервером из дополнительной группы; если подходящий сервер там недоступен — из аварийной. Если основной замер получен уже в дополнительной группе после отказа всех основных, подтверждение ищется в аварийной. При замере из аварийной группы дальнейшей группы для подтверждения нет. Остальные серверы группы с уже полученным валидным замером в этом цикле не проверяются. `low_confirmed` требует просадки **того же направления** на двух разных именах и IPv4. DNS-алиасы того же IPv4 при поиске подтверждения пропускаются с `confirmation_not_independent`. Это сигнал деградации, не доказательство неисправности провайдера. Если второй сервер здоров — `server_disagreement`; поиск прекращается без попытки получить другое мнение из аварийной группы. Если подтверждения нет — `low_unconfirmed`.
5. Каждый восьмой сохранённый цикл проверяет также по одному доступному представителю дополнительной и аварийной групп (около суток при интервале 3 часа). При неудаче выбранного представителя пробуются другие серверы его группы в пределах общего deadline. Это не обход всех серверов за один цикл. Ошибка резерва остаётся в `attempts`/`errors`, не портит успешный primary. Номер цикла и очереди выбора переживают рестарт и очистку старой истории.

Для каждой группы настройка `selection` независима:

- `sequential` — последовательная очередь по списку. Следующий вызов группы начинает с сервера после последнего выбранного; позиция хранится в SQLite отдельно для каждой группы. Если группа не использовалась, её очередь не меняется. После изменения списка сохранённая позиция применяется к новому списку по модулю его длины.
- `random` — новый случайный порядок при каждом вызове группы. Внутри одного цикла серверы группы не повторяются (повторы портов одного сервера регулируются отдельно); между циклами тот же сервер может быть выбран снова. Последовательная очередь в этом режиме не меняется.

В группе нет верхнего ограничения количества серверов. Основная должна содержать хотя бы один сервер, дополнительная и аварийная могут быть пустыми. `id` и hostname должны быть уникальными во всех группах. Общий `cycle_timeout` ограничивает время независимо от размера списков: большой список не означает, что каждый сервер будет проверен за один цикл.

Пример настройки групп; в каждый `servers` можно добавлять объекты того же формата:

```json
{
  "server_groups": {
    "primary": {
      "selection": "random",
      "servers": [
        {"id": "hostkey-msk", "host": "spd-rudp.hostkey.ru", "ports": [5201, 5202], "min_download_mbps": 500, "min_upload_mbps": 500}
      ]
    },
    "additional": {
      "selection": "sequential",
      "servers": [
        {"id": "mts-msk", "host": "mskst.st.mtsws.net", "ports": [3333], "min_download_mbps": 500, "min_upload_mbps": 500}
      ]
    },
    "emergency": {
      "selection": "random",
      "servers": [
        {"id": "ruweb-msk", "host": "msk.speed.ruweb.net", "ports": [5201], "min_download_mbps": 500, "min_upload_mbps": 300}
      ]
    }
  }
}
```

Полный пример со всеми остальными настройками — `config/example.json`.

Пороговые значения — настраиваемые абсолютные Mbps для **каждого сервера и направления**, не объединённая статистическая baseline. Примерные 500/500 и 500/300 не являются универсальной нормой: настройте их под тариф и собственные наблюдения. Адаптивное обучение baseline не реализовано. Значения, полученные ранее на чужом узле, не используются как калибровка.

`mbps` берётся из `end.sum_received.bits_per_second`, TCP retransmits — из `end.sum_sent.retransmits`, если поле присутствует. Нет поля — `null`, не ноль. `latency_ms` и `latency_method` всегда `null`: iperf throughput и TCP RTT под нагрузкой не выдаются за корректную базовую задержку.

## Проверка WAN: возможности и ограничения

До и после **каждого направления** агент сверяет `ip -j -4 route get <resolved endpoint>` с заданными interface/gateway и HTTPS-проверку внешнего IPv4 с разрешёнными CIDR. DNS и guard выполняются в ограниченных по времени дочерних процессах. Proxy-переменные игнорируются для HTTPS-проверки. IPv4 endpoint фиксируется на пару DL/UL. `bind_address` передаётся в iperf3 через `-B` и учитывается при route lookup.

Мастер запрашивает список `route.public_ip_urls`, общий бюджет `verification_timeout` (12 секунд по умолчанию), бюджет одного источника `source_timeout` (3 секунды) и `min_confirmations` (1). По умолчанию используются независимые ipify, icanhazip и AWS checkip. При ошибке DNS/HTTP/timeout проверяется следующий источник; DNS входит в бюджет дочернего процесса. Оставшееся время делится между оставшимися источниками, поэтому один недоступный источник не расходует весь общий бюджет. Проверяются все доступные свидетели: разные IPv4 означают конфликт даже внутри одного разрешённого CIDR. `min_confirmations: 1` позволяет пережить отказ остальных сервисов; поставьте 2 для обязательного согласия двух источников. Это политика доступности, а не голосование: противоречивый ответ всегда блокирует тест.

`route.expected_public_cidrs` — список **ожидаемых внешних адресов вашего основного WAN**. Он нужен, чтобы отличить основной канал от резервного, а не для доступа к серверам iperf. Для статического IPv4 укажите адрес `/32`; для динамического — проверенный диапазон провайдера, исключающий резервный WAN. Пустой список в режиме `required` блокирует тест (`route_unconfigured`). Старый `public_ip_url` читается как список из одного источника; для устойчивости добавьте остальные в мастере.

| Причина в JSON | Значение | Действие |
| --- | --- | --- |
| `route_public_ip_mismatch` | наблюдаемый IPv4 вне ожидаемых CIDR | проверить основной WAN и разрешённый адрес |
| `route_verification_unavailable` | недостаточно успешных ответов | проверить DNS/HTTPS и ошибки источников |
| `route_verification_conflict` | источники вернули разные IPv4 | проверить NAT, PBR, прокси/выходы |
| `route_interface_mismatch` / `route_gateway_mismatch` | локальный маршрут отличается | проверить интерфейс/шлюз |

У каждой WAN-проверки сохраняются `verification_status` и `sources` с URL, IP либо причиной отказа. В `required` любой из этих отказов прекращает цикл **до следующего iperf3**, со статусом `route_blocked`, без WAN-alert. Мастер не отключает защиту автоматически. Осознанный `route.mode: "off"` пропускает guard, пишет `explicitly_disabled` и запрещает `wan_alert`, даже если низкая скорость подтверждена.

Это проверка локального маршрута и внешнего выхода HTTPS-пробы. Она **не доказывает**, что NAT/PBR маршрутизатора направляет iperf и HTTPS одним WAN. При PBR, нескольких source IP или VPN требуется правило на маршрутизаторе, закрепляющее весь исходящий трафик узла (или выбранного source IP) за основным WAN, без fallback на LTE. `bind_address` не привязывает HTTPS-пробу: в сложной многоканальной схеме это особенно важно. Если нужен строгий запрет расходования LTE даже во время переключения в середине теста, обеспечьте его firewall/PBR: проверки до/после не могут остановить мгновенный failover.

`route_blocked` прекращает цикл и исключает WAN-alert; измеренные до изменения маршрута значения остаются в журнале как invalid. Не задавайте слишком широкий разрешённый CIDR, включающий альтернативный WAN. При динамическом адресе используйте поддерживаемый доверенный диапазон или обновляйте локальную конфигурацию после проверки.

## Конфигурация и данные

`config/example.json` перечисляет все настройки. Файл задаётся `--config` или `STOLAS_CONFIG`. Любой верхнеуровневый ключ можно переопределить `STOLAS_<KEY>`: `STOLAS_NODE` — строка, остальные — JSON, например `STOLAS_PARALLEL=4`, `STOLAS_ROUTE='{"mode":"off"}'`, `STOLAS_BIND_ADDRESS='"192.0.2.10"'`. Env приоритетнее файла. Неизвестные ключи/невалидные диапазоны отклоняются. При смене настроек перезапустите API.

Для групп используется `STOLAS_SERVER_GROUPS` с JSON-объектом всех трёх групп. Старые конфигурации с плоским `servers` и переменная `STOLAS_SERVERS` пока поддерживаются: первый сервер становится основной группой, второй — дополнительной, все остальные — аварийной, с `selection: "sequential"`. Установщик читает старый формат и при сохранении записывает `server_groups`, сохраняя пользовательские endpoints. `servers` и `server_groups` нельзя задавать вместе в файле; обе env-переменные тоже конфликтуют. Для нескольких серверов одной роли настройте новый формат явно.

Дополнительно: `STOLAS_DATA_DIR`, `STOLAS_LISTEN`, `STOLAS_PORT`, `STOLAS_API_TOKEN`. `STOLAS_PROJECT_NAME` в `.env` сохраняет принадлежность Compose и истории каталогу установки. `min_interval` по умолчанию 300 секунд, включая неудачные циклы. `process_timeout` — максимум одного iperf, `cycle_timeout` — бюджет всего цикла. `reserve_every`, `attempts_per_server`, `busy_attempts_per_server`, `retry_delay`, thresholds задаются локально. История: SQLite в именованном volume проекта, последние `history_limit` (10000) циклов. `history` экспортирует последние 100; для полного экспорта используйте SQLite backup/read-only tooling. Ошибка записи не маскируется под успешный цикл.

JSON schema version 1: `id`, `node`, UTC `time`, `status`, `wan_alert`, `parameters`, `primary`, `confirmation`, все `attempts`, `errors`, `duration_seconds`. В попытке: server, `group` (`primary`/`additional`/`emergency`), `selection`, hostname/IP/port, причина (`primary`, `fallback`, `confirmation`, `reserve`), отдельные DL/UL, retransmits, длительности, проверки маршрута и ошибки. Поля группы добавлены совместимо: старые записи истории могут их не иметь. Поле результата `primary` означает первый валидный замер цикла и может содержать сервер из дополнительной или аварийной группы — его роль видна по `primary.group`. В runtime-журнале будут реальные адреса endpoints и ваш node id: относитесь к нему как к локальным эксплуатационным данным. `.env`, `config/local.json`, `data/` исключены из Git и Docker context.

## n8n → Telegram

Удобнее выбрать `export` в мастере и импортировать `n8n/local.json` (неактивен). Либо импортируйте шаблон `n8n/stolas.json`: в **Settings** и **Summary settings** задайте endpoint, chat id и `notificationMode`. В **Run Stolas** и **Read summary** выберите один **Header Auth credential**, имя заголовка `Authorization`, значение `Bearer <token из .env>`. В **Telegram alert** выберите Telegram credential с токеном бота. Токены храните в credential store n8n; они отсутствуют в export и Git. Напишите боту /start или добавьте его в нужный чат с правом отправки, проверьте chat id и тестовую отправку. Выполните Manual test, затем включите расписание.

| Режим | Telegram-сообщения |
| --- | --- |
| `alerts_only` (по умолчанию) | подтверждённая просадка WAN, блокировка маршрута, недоступность API/измерений |
| `every_measurement` | отчёт каждого цикла, включая успешный |
| `daily_summary` | сводка предыдущих 24 часов в выбранный час, плюс немедленные критические уведомления как в `alerts_only` |

Обычный отчёт содержит узел, UTC дату/время, DL/UL, сервер, группу/резерв, WAN verification и статус. При недоступном измерении или блокировке маршрута скорости не выводятся. Ежедневная ветка **Daily summary → Read summary** использует сохранённую историю API и отдельный trigger, не POST теста. Она сообщает число циклов/статусы и средние DL/UL валидных первичных пар. Если история очищена или `history_limit` слишком мал, сводка охватывает только оставшиеся записи; пустая история не превращается в нулевую скорость. Час сводки и интервал замеров используют выбранный IANA timezone. В остальных режимах Daily summary отключён.

Workflow шлёт WAN-alert только при `wan_alert: true`. Недоступность API/измерений и блокировка маршрута дают отдельное техническое сообщение с неизвестным состоянием WAN. Занятые серверы никогда не трактуются как падение канала. Неподтверждённые низкие измерения остаются в журнале. Ошибки Telegram видны как failed execution n8n; настройте наблюдение за такими executions. Workflow не выполняет дедупликацию уведомлений: повторение возможно каждые 3 часа. Не публикуйте экспорт после добавления собственных адресов/credentials.

## Проверка после установки и диагностика

В каталоге установки выполните:

```sh
docker compose ps
docker compose logs --tail 30 stolas
docker compose exec stolas python3 -m agent history
```

Сервис должен быть `healthy`; история должна содержать первичный цикл. Это подтверждает запуск агента, но статус цикла отдельно показывает состояние измерения. После cooldown можно повторить один CLI-тест: `docker compose exec stolas python3 -m agent run`. При n8n выполните **Manual test**, убедитесь в ответе Run Stolas, отдельно проверьте доставку Telegram и только затем активируйте workflow. Не включайте одновременно n8n и CLI schedule/cron.

| Симптом | Что проверить |
| --- | --- |
| Загрузчик отказался от каталога | каталог должен быть пустым либо содержать Stolas; выберите другой `--dir`, не удаляйте чужие файлы |
| Нет прав на `/opt` | заранее создайте принадлежащий вам `/opt/stolas` или используйте `$HOME/stolas` |
| Сбой загрузки/контрольной суммы | сеть и существование релиза; временный каталог с архивом/`diagnostic.txt` указан в сообщении, мастер не запущен |
| Уже работает другой установщик | дождитесь завершения; lock-файл удалять не нужно, ОС снимает блокировку при выходе |
| `route_unconfigured` | повторите настройку и задайте ожидаемый WAN IPv4/CIDR, либо осознанно выберите off |
| `route_blocked` | смотрите `attempts[].route_checks[].sources` и таблицу WAN выше; не меняйте guard на off ради прохождения теста |
| `unavailable` / `server_busy` | смотрите порт и `switch_reason`; публичные серверы могут быть заняты, это не диагноз канала |
| `cooldown` / HTTP 429 | выдержите `min_interval` (300 секунд по умолчанию) |
| HTTP 409 | уже идёт цикл; прочитайте последний результат после его завершения |
| n8n не достигает API | проверьте выбранную topology, Docker gateway/VPN IP, TLS и firewall; localhost контейнера отличается от хоста |
| HTTP 401 | сравните credential Bearer с `.env`, особенно после смены токена |
| Telegram молчит | проверьте выбранную политику, chat id, /start и Telegram credential; в alerts_only успешный цикл не отправляется |
| n8n state уже существует | проверьте ID в `n8n/install-state.json`; обновите существующий workflow вручную через export, не создавайте дубликаты |
| Сбой сборки/обновления | `.stolas-install-status.json` показывает этап и результат восстановления; исходники сохранены в `.stolas-backups`, Docker build выводится в терминал |

Коды выхода мастера: **0** — установка завершена (низкая скорость сама по себе не ошибка установки), **2** — агент запущен, но первый замер `route_blocked`/`unavailable`, **1** — установка/подключение не завершено. После исправления причины повторите команду. Измерения и настроенный агент остаются на месте. Не публикуйте `.env`, `.bak-*`, SQLite и локальные адреса из диагностических результатов.

## Проверка и воспроизводимость

```sh
python3 -m unittest discover -s tests -v
docker build -t stolas:test .
docker run --rm --read-only --tmpfs /tmp --cap-drop ALL \
  -v "$PWD/tests:/tests:ro" --entrypoint python3 stolas:test \
  -m unittest discover -s /tests -v
```

Тесты проверяют busy/fallback, низкую скорость и подтверждение, несколько WAN-источников и hard timeout DNS, историю/сводки, блокировку, cooldown, конфигурацию, настоящий HTTP API, установку через pipe/checkout, обновление/откат и настоящий iperf3 на loopback. Публичные speed-серверы тестами не нагружаются. Без установленного iperf3 loopback test явно skipped; в Docker он обязателен. CI собирает production-образ, повторяет тесты внутри него, исполняет JavaScript уведомлений и импортирует все три варианта workflow в закреплённый n8n 2.x.

Docker: Alpine 3.23.0 закреплён manifest digest; полный набор APK для amd64/arm64 закреплён URL, версией и SHA-256 в `config/apk.lock.json` и `.lock`. Установка идёт без обращения к текущему APKINDEX. Изменение/удаление upstream APK завершает сборку ошибкой; для долгосрочного архива храните APK в собственном неизменяемом mirror. Это воспроизводимость входных зависимостей, не обещание побитово одинакового image ID. Обновление lock: `python3 tools/lock_apk.py`, затем review diff и тестовая сборка. CI Actions также закреплены SHA.
