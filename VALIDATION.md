# Проверка Stolas

## Политика и границы покрытия

До первого стабильного публичного релиза Stolas проверяет чистую установку,
обновление текущей установки и восстановление её локальных снимков.
Миграции с 0.4.0/0.5.0 и архивное хранение старых образов/APK не поддерживаются.
Это не разрешает удалять неизвестные пользовательские файлы или повреждённые
точки восстановления. Подробности — в [политике совместимости](docs/INSTALLATION.md#политика-совместимости).

Набор организован вокруг границ риска. Большинство поведения проверяется
небольшими автономными тестами; текущая установка и восстановление — несколькими
сквозными Docker-сценариями. Нет матриц цветов, отступов, ширины терминала,
исторических конфигураций и всех возможных ответов мастера. Проверки конкретных
регрессий потери данных, утечки токенов и неверных измерений сохраняются отдельно.
Новые проверки добавляются при изменении поведения или обнаруженном дефекте.

| Функция | Основные проверки (`tests/`) |
| --- | --- |
| Скорость, ошибки, резервные серверы, SQLite | `test_agent.py`, `test_groups.py`; реальный loopback iperf3 в `test_ip_user_agent.py` |
| WAN guard и диагностика | `test_wan_routing.py`, локальные TLS/DNS/timeout-проверки в `test_ip_user_agent.py`; `diagnose` в Docker-сценарии |
| CLI/API и авторизация | `test_agent.py`, `test_progress.py`, CLI/API реальной установки в `test_runtime_docker.py` |
| Чистая установка | `test_bootstrap.py`, `test_installer.py`, один PTY-сеанс в `test_terminal.py`, Docker-установка |
| Текущее обновление, SQLite, настройки и токен | `test_runtime.py`, `test_port_update.py`, реальные транзакции в `test_runtime_docker.py` |
| Снимки, откат, права владельца | `test_backup_retention.py`, `test_permissions.py`, неуспешное обновление и явный откат в Docker |
| Zombie-процессы и SIGTERM | `test_process_lifecycle.py`, `ContainerProcessTests` в `test_runtime_docker.py` |
| Секреты, TLS и чужие ресурсы | `test_integration_transport.py`, `test_events.py`, `test_publication.py`, `test_entrypoints.py`, `test_runtime.py` |
| n8n | Экспорт и импорт с существующими credentials в `test_integrations.py`, две реальные сети в `test_environment.py`, `workflow.test.cjs` |
| Закреплённые APK | `test_apk_lock.py`, preflight обеих архитектур в `test_artifacts.py` |

Сквозной Docker-набор проверяет пустую историю до явного измерения, обе скорости,
сохранение строки SQLite через CLI/API, неизменность volume и конфигурации,
снимки, откат после передачи управления неуспешному обновлению, повторное
обновление, перенастройку при cooldown и блокировке измерений. Проверяются
приватные права, отказ прежнего неверного токена и сохранность соседнего контейнера,
чужих файлов и общих Docker-ресурсов. Успех определяется состоянием сервиса
и данных, а не наличием фразы об успехе в терминале.

Остаются риски: редкие сочетания ответов мастера, точное оформление сообщений,
альтернативные n8n-топологии и все перестановки некорректного ввода теперь
не проверяются исчерпывающе. Синтетические Docker-фикстуры не заменяют реальные
сценарии. Тесты не подтверждают работу на production или скорость внешнего канала.

## Локальные проверки

```sh
python3 tools/check_publication.py
python3 -m unittest discover -s tests -v
node tests/workflow.test.cjs
python3 -m agent validate --config config/example.json
git diff --check
```

Все данные установки временные; сетевые измерения и TLS/DNS-регрессии используют
loopback и синтетические адреса. Происхождение фикстур описано в
[tests/fixtures/README.md](tests/fixtures/README.md). Для локального реального
измерения нужны `iperf3` и `ip`; в Core-образе они уже есть. Python использует
только стандартную библиотеку. PTY-тест сохраняет фактический вывод в файл,
если задан `STOLAS_TTY_ARTIFACT`.

## Полная Linux/Docker-матрица

`.github/workflows/ci.yml` остаётся источником полного CI: публикационные данные,
Python, PTY-артефакт, shell-синтаксис, sudo/владение файлами, Node, импорт трёх
workflows в закреплённый n8n, реальный API n8n, Alloy, конфигурация Core,
Docker-сборка, runtime-сценарии, две Docker-сети, тесты с реальным iperf3 внутри
образа и Compose. Интеграционные этапы не отключены. Старое название шага CI
с номерами 0.4.0/0.5.0 не соответствует его содержимому: команда запускает
только текущие runtime-сценарии.

В подготовленной изолированной среде дополнительные Python-проверки запускаются так:

```sh
STOLAS_PRIVILEGED_TEST=1 python3 -m unittest discover -s tests -p test_permissions.py -v
STOLAS_N8N_INTEGRATION=1 python3 -m unittest discover -s tests -p test_integrations.py -v
STOLAS_RUNTIME_DOCKER=1 python3 -m unittest discover -s tests -p test_runtime_docker.py -v
STOLAS_DOCKER_INTEGRATION=1 python3 -m unittest discover -s tests -p test_environment.py -v
```

Docker runtime-сценариям нужен собранный `stolas:ci`, доступ к локальному Docker
и свободное имя контейнера `stolas`. Они не предназначены для рабочего сервера.
Перед сборками проверяй загрузку VM, память, диск и чужие активные задачи.
Не останавливай чужие контейнеры ради тестов. Пропуск интеграционного теста
означает отсутствие результата в этой среде, а не успех.

## Дочерние процессы и завершение контейнера

Регрессия Issue #41 воспроизводится при таймауте shell-формы Docker healthcheck:
Docker завершает `/bin/sh -c`, а Python проверки остаётся жив, переходит к Core
(PID 1) и после выхода остаётся zombie. Это воспроизведено в изолированном
контейнере без измерений и внешней сети. Интервал 15 секунд вместе с таймаутом
5 секунд объясняет возможные серии с шагом около 20 секунд. Состояние исторического
рабочего контейнера не менялось; воспроизведение подтверждает механизм в коде.

Healthcheck использует exec-форму: Docker запускает, завершает и ожидает сам
Python-процесс. URL, токен, авторизация, таймаут HTTP и критерий здоровья сохранены.
Core остаётся PID 1; `init: true`, глобальный обработчик SIGCHLD и сторонний init
не добавляются. Общий `waitpid(-1)` мог бы перехватить статусы процессов, которыми
управляет `subprocess`. Исправление устраняет конкретный источник осиротевших
процессов, но не превращает Core в универсальный init для произвольных команд
`docker exec`, которые сами бросают потомков.

```sh
python3 -m unittest discover -s tests -p test_process_lifecycle.py -v
STOLAS_RUNTIME_DOCKER=1 python3 -m unittest discover -s tests -p test_runtime_docker.py -k ContainerProcessTests -v
```

Первая команда на Linux запускает настоящие Python-процессы resolver/worker и
синтетический заменитель iperf. Повторяются успешные и неудачные измерения,
таймауты и отмена; отсутствие PID в `/proc` проверяется до любых дополнительных
`poll()`/`wait()`, затем `waitpid` подтверждает, что статус уже собран. Также
проверяется отсутствие накопления потоков обмена. Реальный iperf отдельно
покрывается loopback-тестами и тестами внутри образа.

Docker-проверки используют собранный `stolas:ci`, его штатный healthcheck и
искусственную задержку старта только процесса проверки. Повторяются ошибки,
таймауты и восстановление здоровья; в namespace не должно оставаться zombie
или усыновлённых Core процессов. SIGTERM проверяется без измерения и во время
зависшей DNS-пробы: контейнер выходит с кодом 0 без SIGKILL, сообщает
`service_stopped`, сохраняет ранее записанную SQLite-историю и конфигурацию.
При остановке контейнера незавершённое измерение прерывается вместе с его
PID namespace; это не обещание завершить или сохранить частичный результат.

Изменение healthcheck применяется при пересоздании контейнера из нового образа
в рамках обычного обновления; уже запущенные контейнеры оно не меняет.

## Закреплённые Alpine APK

Перед Docker-сборкой проверь доступность и SHA-256 всех закреплённых APK:

```sh
python3 tools/lock_apk.py --check
```

Команда проверяет согласованность JSON, текстовых lock-файлов и базового образа,
скачивает каждый APK обеих архитектур и сравнивает SHA-256. Она не обновляет
версии и не обращается к индексу пакетов. Проверяются также имена, версии и
архитектуры в URL. Для временных ошибок DNS/соединения, таймаутов, обрыва ответа
и HTTP 408/429/500/502/503/504 предусмотрены до трёх попыток с паузами 1 и 2 секунды
и таймаутом сокета 30 секунд. Исчерпание попыток остаётся ошибкой проверки,
а не успешным пропуском. HTTP 404, ошибки TLS и несовпадение SHA-256 не повторяются
и не обходятся. Нужен доступ к Alpine CDN. Сообщения не выводят тела ответов
и содержимое сетевых исключений; URL с credentials, query или fragment запрещены.

В GitHub Actions эта проверка входит в `tests/test_artifacts.py` и выполняется
существующим шагом Python-тестов до основной Docker-сборки. Вне Actions она
включается через `STOLAS_APK_INTEGRATION=1`; обычные локальные тесты не требуют
внешней сети. Отдельные автономные регрессионные тесты находятся в
`tests/test_apk_lock.py`.

Репозиторий Alpine `v3.23/main` изменяется: старые APK могут исчезнуть после
обновления пакета. Фиксация версии и SHA-256 защищает содержимое, но не гарантирует
хранение файла upstream. Для намеренного обновления зависимостей запусти
`python3 tools/lock_apk.py`, проверь diff всех трёх `config/apk*.lock*`, затем
повтори `--check`, тесты и Docker-сборку. Генератор заменяет lock-файлы только
после успешного скачивания полного набора обеих архитектур. Каждый файл заменяется
через атомарный rename; при ошибке или KeyboardInterrupt публикация откатывается
к прежним файлам. Три отдельных файла не образуют атомарную транзакцию для
параллельного читателя: не запускай генерацию одновременно со сборкой.
Каталог `config/.apk-lock-update` блокирует повторную публикацию и preflight
во время обновления или после аварийного завершения. При неудачном откате
копии остаются в его подкаталоге `original`; после SIGKILL или сбоя питания
требуется ручная проверка и восстановление согласованного набора перед удалением
этого каталога. Гарантии сохранности при сбое диска/питания нет.
Автоматически перегенерировать lock при 404 или несовпадении хеша нельзя.

Сборка воспроизводима по закреплённому содержимому, пока APK и базовый OCI-образ
доступны. Долговременная доступность удалённых upstream артефактов не гарантируется;
до стабильного публичного релиза отдельное архивное хранилище не поддерживается.
При 404 требуется явное обновление текущих pins с проверкой полного набора,
подписей, зависимостей и сборки. SHA-256, preflight и `apk add --no-network`
сохраняются. Автоматическая подмена зависимостей не допускается.

## Данные для публикации

В примерах используйте домены `example.test`, `example.net` и IPv4 из
192.0.2.0/24, 198.51.100.0/24, 203.0.113.0/24. LAN/Docker/VPN-адреса в
модульных тестах синтетические. Реальные имена узлов, IP, топологию,
локальные конфигурации, токены, логи и снимки рабочих систем не коммитить.

`tools/check_publication.py` проверяет отслеживаемые файлы и вложенные архивы.
Автоматическая проверка дополняет ручной просмотр: произвольное имя узла
в обычном тексте не всегда можно отличить от безопасного примера.
