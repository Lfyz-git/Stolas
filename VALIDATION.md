# Проверка Stolas

## Регрессии v0.6.5

Оба клиентских URL проверяются с HTTP/HTTPS, синтетическими LAN/overlay IP,
доменом и адресом из документационного диапазона. Подтверждение каждого HTTP
обязательно, по умолчанию отмена; отказ не запрашивает ключ, не применяет
настройки и не вызывает запросов с ключом. Общий валидатор остальных сценариев
сохраняет прежние ограничения HTTPS. Проверка локального bind остаётся отдельной.

Локальные HTTP/TLS-серверы проверяют, что перенаправления не получают ключи,
а недоверенный сертификат отклоняется до передачи HTTP-заголовков. Ошибки DNS,
отказа соединения, таймаута и TLS не раскрывают содержимое исключений.
Изолированный n8n 2.42.6 проходит мастер с двумя подтверждениями HTTP и реальный
API-импорт с сохранением адреса и переиспользованием существующих credentials;
проверка Core в этом API-тесте заменена заглушкой и покрывается отдельно.

Начиная с v0.6.0 Stolas использует новую Git-историю. Данные примеров и исторические
фикстуры миграции очищены и документированы отдельно.

## Локальные проверки

```sh
python3 tools/check_publication.py
python3 -m unittest discover -s tests -v
node tests/workflow.test.cjs
python3 -m agent validate --config config/example.json
```

Python-тесты проверяют выбор серверов, WAN guard, HTTP API, хранение истории,
установку, владение ресурсами, обновление, восстановление и уведомления.
HTTPS-проверки используют локальный сервер и публичный тестовый сертификат.
Проверки миграции используют очищенные исторические исходники, а не копии
рабочих установок. Происхождение данных описано в [fixtures](tests/fixtures/README.md).

## Linux и Docker

Полная матрица задана в `.github/workflows/ci.yml`: shell-синтаксис,
терминальный интерфейс, sudo и права владельца, реальный iperf3, миграция Docker,
импорт n8n и валидация Alloy. Часть этих проверок требует Linux/Docker и
включается переменными `STOLAS_*_INTEGRATION`, `STOLAS_RUNTIME_DOCKER`,
`STOLAS_PRIVILEGED_TEST`. Пропуск теста означает отсутствие проверки в этой среде.

Успешные локальные тесты не подтверждают доступность внешних сервисов,
пропускную способность реального канала или работу на конкретном узле.
Перед выпуском выполняется полная матрица Linux/Docker CI.
Результаты прошлых развёртываний и старые журналы CI сюда не перенесены.

## Закреплённые Alpine APK

Перед Docker-сборкой проверь доступность и SHA-256 всех закреплённых APK:

```sh
python3 tools/lock_apk.py --check
```

Команда проверяет согласованность JSON, текстовых lock-файлов и базового образа,
скачивает каждый APK обеих архитектур и сравнивает SHA-256. Она не обновляет
версии и не обращается к индексу пакетов. Проверяются также имена, версии и
архитектуры в URL. Для временных ошибок DNS/соединения, таймаутов, обрыва ответа
и HTTP 408/429/500/502/503/504 предусмотрены до трёх попыток с паузами 1 и 2 секунды
и таймаутом сокета 30 секунд. Исчерпание попыток остаётся ошибкой проверки,
а не успешным пропуском. HTTP 404, ошибки TLS и несовпадение SHA-256 не повторяются
и не обходятся. Нужен доступ к Alpine CDN. Сообщения не выводят тела ответов
и содержимое сетевых исключений; URL с credentials, query или fragment запрещены.

В GitHub Actions эта проверка входит в `tests/test_artifacts.py` и выполняется
существующим шагом Python-тестов до основной Docker-сборки. Вне Actions она
включается через `STOLAS_APK_INTEGRATION=1`; обычные локальные тесты не требуют
внешней сети. Отдельные автономные регрессионные тесты находятся в
`tests/test_apk_lock.py`.

Репозиторий Alpine `v3.23/main` изменяется: старые APK могут исчезнуть после
обновления пакета. Фиксация версии и SHA-256 защищает содержимое, но не гарантирует
хранение файла upstream. Для намеренного обновления зависимостей запусти
`python3 tools/lock_apk.py`, проверь diff всех трёх `config/apk*.lock*`, затем
повтори `--check`, тесты и Docker-сборку. Генератор заменяет lock-файлы только
после успешного скачивания полного набора обеих архитектур. Каждый файл заменяется
через атомарный rename; при ошибке или KeyboardInterrupt публикация откатывается
к прежним файлам. Три отдельных файла не образуют атомарную транзакцию для
параллельного читателя: не запускай генерацию одновременно со сборкой.
Каталог `config/.apk-lock-update` блокирует повторную публикацию и preflight
во время обновления или после аварийного завершения. При неудачном откате
копии остаются в его подкаталоге `original`; после SIGKILL или сбоя питания
требуется ручная проверка и восстановление согласованного набора перед удалением
этого каталога. Гарантии сохранности при сбое диска/питания нет.
Автоматически перегенерировать lock при 404 или несовпадении хеша нельзя.

Долговременная воспроизводимость требует отдельного неизменяемого снимка полного
набора APK обеих архитектур и сохранения базового OCI-образа по digest. При
организации такого хранилища нужно проверять APK по уже утверждённым SHA-256,
фиксировать HTTPS URL снимка в JSON и текстовых lock-файлах без изменения хешей,
сохранять проверку подписей APK и установку `apk add --no-network`. Доступность
снимка должна проверяться тем же preflight. Эта правка обновляет текущие pins
и обнаруживает их недоступность заранее; внешнее хранилище она не создаёт.

## Данные для публикации

В примерах используйте домены `example.test`, `example.net` и IPv4 из
192.0.2.0/24, 198.51.100.0/24, 203.0.113.0/24. LAN/Docker/VPN-адреса в
модульных тестах синтетические. Реальные имена узлов, IP, топологию,
локальные конфигурации, токены, логи и снимки рабочих систем не коммитить.

`tools/check_publication.py` проверяет отслеживаемые файлы и вложенные архивы.
Автоматическая проверка дополняет ручной просмотр: произвольное имя узла
в обычном тексте не всегда можно отличить от безопасного примера.

## Проверки v0.6.0

Полная локальная матрица выполнена в Linux с нативным Docker Engine:
255 Python-тестов без пропусков, включая реальные Docker-сети, миграции
v0.4.0/v0.5.0, откат, sudo, iperf3 и API n8n. Проверены сборка образа,
уведомления, импорт трёх n8n workflows, Alloy, Compose и production image.
Внутри production image проходят 79 runtime-тестов; 176 проверок установщика
и инструментов разработки пропускаются, поскольку их исходников в образе нет.
GitHub Actions повторяет матрицу на чистом Ubuntu runner перед выпуском.

## Регрессии v0.6.1

Проверки WAN дополнены искусственной задержкой запуска Python на 3,6 секунды,
быстрым локальным HTTPS-источником с `source_timeout=3`, зависшим DNS,
резервным источником после таймаута и жёстким общим сроком. Отдельный тест
проверяет полный цикл download/upload с реальным локальным iperf3, включённым
WAN guard и четырьмя успешными проверками маршрута через резервный источник.
Все адреса и ожидаемые внешние IP в этих проверках синтетические.

## Регрессии v0.6.4

Проверяются успешная фиксация и сообщение об установленной версии, отказ
установщика, ошибка финализации, отмена и прерывание. Ошибки очистки точек
восстановления не меняют успешный результат обновления и не требуют его повторять.
Отчёт проверяется на сочетании трёх сохранённых и трёх старых точек, при полном,
частичном и нулевом удалении, повторном запуске и ширине терминала 32 символа.
Учитываются только фактически удалённые каталоги за текущую операцию.

`stolas version` и help проверяются с запрещёнными сетью, Docker и subprocess.
Покрыты отсутствующие, повреждённые, недоступные и связанные ссылкой метаданные,
незавершённое обновление и Core старее инструмента управления. Реальная Docker-
миграция дополнительно проверяет сообщение об обновлении и CLI `version` до и
после отката на v0.5.0.

## Регрессии v0.6.3

Перенастройка проверяется без нагрузочного теста при cooldown, занятой блокировке
и недоступном измерительном сервере. Ошибки конфигурации, запуска контейнера,
доступности и авторизации API остаются ошибками. На временной реальной Docker-
установке выполняется измерение с loopback iperf3, затем CLI `configure` меняет
настройки при подтверждённом cooldown и реальной `flock` блокировке в отдельном
контейнере. Проверяются сохранение строки SQLite через API, неизменность volume,
успешная фиксация транзакций и сходимость к трём обычным копиям.

Смешанные legacy/complete/rolled_back снимки проверяются с положительными
свидетельствами и без них, с конфликтующим активным журналом, повторными запусками,
ошибками записи/удаления, ссылками и FIFO. Отчёт за операцию должен быть один,
с фактическими количествами и причинами, без приватного содержимого исключений.

## Регрессии v0.6.2

Повторное использование процесса проверяется восемью свежими HTTPS-запросами,
таймаутами DNS, завершением зависшего процесса и жёстким сроком запуска.
Смена внешнего IP блокирует результат после download, перед upload и после
upload. Существующие проверки независимого подтверждения, резервного обхода,
busy-портов и повторов сохраняются.

Тесты хранения транзакций покрывают 0–6 копий, порядок при одинаковых временных
метках и переводе часов назад, активные/прерванные снимки, откат, повреждение
метаданных, ссылки, ошибки удаления и повторные update/reconfigure. Данные
настроек и истории проверяются отдельно от удаляемых снимков.

Сравнение полного локального цикла до/после с искусственной задержкой запуска
Python описано в [заметках к релизу](docs/RELEASE-v0.6.2.md). Значения `timings`
в результатах позволяют проверить накладные расходы на собственной установке
без публикации её конфигурации и адресов.

Мастер n8n проверяется для Docker, локального приложения и другого хоста:
обычный/overlay IPv4, ручной ввод, loopback с HTTPS endpoint, подтверждение HTTP
и wildcard, недопустимые/отсутствующие привязки и перенос старых схем. Отдельный
тест выполняет мастер и авторизованную проверку из контейнера n8n в двух реальных
Docker-сетях; импорт credentials/workflow проверяется в изолированном n8n.
